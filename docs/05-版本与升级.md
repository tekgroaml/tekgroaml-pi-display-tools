# 版本与升级

## 三种版本各管什么

| 标识 | 位置 | 用途 |
| --- | --- | --- |
| 应用版本，例如`2.1.0` | 仓库根目录`VERSION.json`的`version` | 区分功能、修复与发布包 |
| 命令接口版本，目前`2` | `command_version` | 表明命令契约；接口版本2使用统一的1/2编号 |
| 配置格式版本，目前均为`1` | `config_versions`及各配置文件的`version` | 判断显示设置、触摸映射、运行状态能否被新版本读取 |

`VERSION.json`是应用版本与兼容性声明的唯一来源，Python的`__version__`及三个命令的版本输出由它读取。应用从2.0升级到2.1，不代表配置JSON也要改成2.1。

## 如何给一次改动定版本

本项目采用[语义化版本](https://semver.org/)的主版本、功能版本和修复版本含义，当前发布流程只接受稳定的`X.Y.Z`数字版本，不接受预发布、构建后缀或前导零。

| 改动 | 示例 |
| --- | --- |
| 不兼容的命令、行为或接口改动 | `2.1.3` → `3.0.0` |
| 向后兼容的新功能、新模式或管理命令 | `2.0.0` → `2.1.0` |
| 向后兼容的问题修复、安装修复或说明纠正 | `2.1.0` → `2.1.1` |

例如统一`--port`编号属于2.0的大版本改动；增加版本查询与升级管理属于2.1.0的兼容功能扩展；新增受保护的长条屏兼容配置档属于2.2.0的兼容功能扩展。配置格式仍为1，命令编号仍为1/2。

安装包指纹包括代码、安装脚本、服务和随包文档。相同版本号应对应相同发布内容；修改这些内容后也要升版本，不能覆盖已发布的同号包。FAQ仓库的独立文档更新不改变应用指纹。

## 查看版本

```bash
pi-setting version
pi-setting version --json
pi-setting --version
screen-config --version
screen-test --version
```

`version`会显示：当前执行代码版本、已安装版本、命令接口版本、配置格式、安装时间和完整性状态。它不要求图形桌面运行。

从源码目录运行`bin/pi-setting`时，源码版本可能比已安装应用更新，两者会分开显示。旧1.0/2.0安装没有安装凭据，显示`legacy-unrecorded`是正常的；不会为了读取版本执行旧版代码。

## 检查目标版本

先获取可信的目标源码目录，再比较：

```bash
pi-setting check-update --source ~/pi-setting
```

此命令比较“已下载目录”与“已安装应用”，**不会联网查找最新版，也不会下载或修改应用**。网络断开时，只要目标目录已完整下载，也能检查。

输出包含`installed_version`、`target_version`、`action`、`allowed`、配置版本与内容SHA256。返回码0表示判断完成且允许该计划，2表示计划被版本策略拒绝，1表示元数据、配置或文件存在错误。

| 情况 | 处理 |
| --- | --- |
| 未安装 | `install`：允许首次安装 |
| 同版本、同内容、命令入口完整 | `noop`：跳过，不重复安装依赖 |
| 同版本但命令已卸载/丢失 | 要求显式`--reinstall`修复 |
| 同版本却提供不同内容 | 拒绝，维护者必须使用新版本号 |
| 较新的同主版本 | `upgrade`：允许，仍检查配置格式 |
| 跨主版本 | 默认拒绝，阅读变更记录后加`--allow-major` |
| 较旧版本 | 拒绝降级，`--allow-major`也不会放行 |
| 低于最低可升级版本 | 拒绝，需要单独迁移方案 |
| 未知配置格式或配置损坏 | 在替换程序前拒绝 |
| 已安装代码被手工改动 | 拒绝覆盖，先保留本地改动；同发布包可用`--reinstall`修复 |

## 执行升级

```bash
sudo pi-setting upgrade --source ~/pi-setting
```

只有依赖已经齐全时可增加`--no-deps`，跳过apt依赖操作：

```bash
sudo pi-setting upgrade --source ~/pi-setting --no-deps
```

也可以直接使用下载包的安装入口，判断规则相同：

```bash
cd ~/pi-setting
sudo bash scripts/install.sh
```

旧2.0及更早版本没有`pi-setting`管理命令，首次升级到2.1时使用上面的安装脚本。1.x升到2.x属于跨主版本，还需要`--allow-major`，并更新旧脚本的端口参数。

跨主版本与同版本修复示例：

```bash
sudo pi-setting upgrade --source ~/pi-setting --allow-major
sudo pi-setting upgrade --source ~/pi-setting --reinstall
```

`upgrade`调用目标目录内的安装程序，由目标版本再次执行升级判断。只使用可信仓库或可信下载包；SHA256用于识别内容变化，不等同于发布者签名认证。

## 升级时如何保护当前设置

1. 比较应用版本，读取配置格式，校验完整的目标包。
2. 检查平台和依赖；在旁边临时目录准备新应用。
3. 备份旧应用、显示/触摸配置、命令入口和服务文件。
4. 停止现有颜色测试；若触摸中转服务正在运行，也会短暂停止。
5. 切换新应用、验证文件指纹和配置格式，写入安装凭据。
6. 恢复触摸服务与之前的测试模式。测试颜色、计数及轨迹从初始状态重新开始。

不会为普通应用升级重新编号保存JSON、重设分辨率或重新猜测USB配对。当前没有定义任何配置格式迁移器；未来若更改配置格式，必须先实现、测试明确的迁移路径，不能只修改数字跳过检查。

安装凭据：`/var/lib/pi-setting/installation.json`。记录版本、前一版本、时间、兼容格式、内容SHA256及本机备份目录。备份位于`/var/lib/pi-setting/install-backups/`。

文件与服务切换阶段失败时，程序会回退旧应用和已备份的配置，并尝试恢复服务与测试。apt已安装的系统依赖不会回退；断电、存储损坏或回退自身失败不在该机制的保证范围内。测试画面恢复失败会给出提示，不把它伪装为已恢复。

本次不提供任意版本降级命令。需要回退历史发布或手动恢复备份时，由维护人员核对应用与配置兼容性后处理。

## 发布者流程

1. 修改`VERSION.json`中的版本；配置格式不变时保持对应版本为1。
2. 更新`CHANGELOG.md`，列出不兼容项与已验证范围。
3. 运行测试、语法检查和发布内容扫描，提交全部发布文件。
4. 为该提交创建同号Git标签，如`v2.1.0`；不要移动已公开标签或覆盖同号内容。
5. 推送提交和标签。用户可以下载指定标签，而不是依赖会继续变化的`main`。

`main`可用于开发；正式发布包应固定到版本标签。若目标标签尚未发布，不要向客户提供假定存在的下载地址。
